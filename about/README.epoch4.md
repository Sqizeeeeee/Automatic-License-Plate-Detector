# Epoch 4: замена OCR-движка, стабилизация фото-пайплайна

## Контекст

К началу этой эпохи детектор номерных знаков (YOLOv8) и обработка фото были
реализованы и работали стабильно. Узким местом оставалось распознавание
текста: используемый RapidOCR регулярно терял символы, путал похожие
символы и галлюцинировал лишние символы на номерах со сложной текстурой
фона. Подробное описание проблем и первоначальный план решения приведены
в `OCR_TASK.md`.

Работа с видеопотоком в этой эпохе не велась. Видео обрабатывается тем же
пайплайном, что и фото (см. `video_processor.py`), поэтому любые улучшения
распознавания текста автоматически применяются и к видео, но отдельного
внимания видеопотоку не уделялось: известные проблемы стабильности между
кадрами не устранялись.

## Архитектура системы на конец эпохи

```
Фото → PlateDetector (YOLOv8 + deskew) → PlateReader (fast-plate-ocr) → результат
```

### Точка входа

`app/bot.py` — Telegram-бот на aiogram. Обрабатывает входящие фото и видео,
вызывает `ImageProcessor`/`VideoProcessor`, форматирует ответ пользователю.

### Детекция номера

`app/detector.py`, класс `PlateDetector`.

- Модель: YOLOv8, веса `weights/detector_best.pt`.
- `find_plate(image)` возвращает один кроп найденного номера (первый бокс
  с confidence >= 0.5) или `None`, если номер не найден.
- После детекции кроп проходит через `deskew_plate` — коррекцию перспективы
  на основе минимального ограничивающего прямоугольника вокруг крупнейшего
  контура. Deskew применяется только если найденный контур занимает не
  менее 60% ширины кропа и соотношение сторон получившегося прямоугольника
  лежит в диапазоне 1.5–6, иначе возвращается исходный (не выпрямленный)
  кроп.

Эта часть не менялась в текущей эпохе.

### Препроцессинг

`app/preprocessor.py`, класс `PlatePreprocessor`. Апскейлинг кропа до
целевой ширины (кубическая интерполяция), CLAHE для выравнивания
локального контраста, unsharp masking.

В текущей эпохе препроцессор не подключён к OCR-пайплайну: новая модель
распознавания принимает исходный кроп без дополнительной обработки (см.
раздел "Решения и компромиссы" ниже и `OCR_README.md`).

### Распознавание текста

`app/ocr_engine.py`, класс `PlateReader`. Подробное описание того, как
устроена и обучена эта часть, вынесено в `OCR_README.md`.

### Оркестрация

`app/image_processor.py`, класс `ImageProcessor` — связывает детектор и
ридер для одного изображения, выполняет блокирующие вызовы в отдельных
потоках через `asyncio.to_thread`, чтобы не блокировать event loop бота.

Контракт между компонентами:

```python
detector.find_plate(image: np.ndarray) -> np.ndarray | None
reader.read_plate(plate_crop: np.ndarray) -> tuple[str | None, str | None]
# второй элемент — "high" | "mid" | "low" | None
```

## Что изменилось в этой эпохе

1. RapidOCR полностью удалён из пайплайна и из зависимостей проекта.
2. Собран и провалидирован датасет номерных знаков (Европа и США,
   1813 записей) из четырёх источников. Подробности сбора — в
   `OCR_README.md`.
3. Проведён fine-tuning модели `cct-s-v2-global` (fast-plate-ocr) на этом
   датасете. Точность полного совпадения номера (`plate_acc`) выросла с
   87.85% (предобученная модель без дообучения) до 94.48% на отложенной
   выборке.
4. `PlateReader` переписан поверх `LicensePlateRecognizer` из
   `fast-plate-ocr`, интерфейс класса (`read_plate`) сохранён без
   изменений, поэтому остальной код приложения не потребовал правок.
5. Веса моделей (детектора и OCR) вынесены в единую директорию `weights/`
   в корне проекта.
6. Зависимости разделены по назначению: `requirements.txt` содержит только
   то, что нужно приложению в проде, `requirements-dev.txt` — инструменты
   разработки (ruff), `ocr_model/requirements.txt` — зависимости, нужные
   только для обучения OCR-модели.

## Решения и компромиссы

- **Препроцессор перед OCR временно отключён.** Он был настроен под
  RapidOCR и не тестировался с новой моделью. Первые тесты на прежде
  проблемных случаях (см. `OCR_TASK.md`) показали корректное распознавание
  без него, поэтому решено не усложнять пайплайн, пока не появится
  конкретная причина вернуть препроцессинг.
- **Региональная голова модели (страна происхождения номера) не
  дообучалась.** В собранном датасете нет разметки по конкретным странам
  — только по паре "eu"/"us", и присвоение всем европейским записям
  значения "Unknown" при обучении испортило бы то, что предобученная
  модель уже умела определять. Вес функции потерь для регионной головы
  при обучении был выставлен в 0, поэтому её веса остались нетронутыми.
  Функциональность определения региона в приложении не задействована и
  не тестировалась.
- **Обучение проводилось на CPU** (Apple Silicon, M4 Pro). Попытка
  задействовать Metal-ускорение через `tensorflow-metal` не удалась
  из-за несовместимости версий с установленным TensorFlow; поскольку
  время обучения на CPU оказалось приемлемым (менее часа на полный цикл
  с early stopping), решение проблемы с GPU было отложено как
  не первоочередное.

## Известные ограничения на конец эпохи

- Видеопоток не тестировался и не дорабатывался в этой эпохе.
- Пороги уверенности (`high`/`mid`/`low`) унаследованы от старой
  реализации на RapidOCR (0.9 и 0.6) и не пересматривались под новую
  модель.
- Региональная разметка в датасете грубая (eu/us, без указания страны),
  что ограничивает точность определения региона, если эта функция когда-
  либо понадобится.
- Планируется перенос системы на сервер или Raspberry Pi; выбор ONNX как
  формата инференса для OCR сделан с учётом этого требования, но перенос
  сам по себе ещё не выполнялся и не тестировался.

## Дальнейшие направления

- Прогнать регрессионный тест: сравнить метрику `PlateReader` внутри
  приложения с метрикой, полученной через `fast-plate-ocr valid` на том
  же val-датасете, чтобы подтвердить отсутствие потерь качества при
  интеграции.
- При необходимости пересмотреть пороги confidence под новую модель.
- Вернуться к стабильности распознавания на видео, если это станет
  актуальным.
